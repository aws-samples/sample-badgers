Product overview

Make complex documents usable, reviewable, and ready for action.

From historical manuscripts, maps, and annotated scans to invoices, Word documents, and PowerPoint decks, BADGERS preserves the parts of a document that plain text extraction loses: hierarchy, layout, tables, figures, handwriting, reading order, and the evidence behind a result.

One platform, three product boundaries
Full · Headless · Specialists

Choose the experience your team needs without changing the underlying document intelligence, specialist definitions, or release process.

● Human workbench and reports ● Durable application integration ● Direct AWS-native tools

The value proposition

Not just text extraction: a traceable document understanding workflow.

BADGERS combines specialist analysis with structured artifacts so teams can work with the document’s content and verify how an answer was reached.

Why BADGERS is different: most extraction tools turn a document into text. BADGERS retains the structure and visual relationships that give text meaning, then uses native parsing, OCR, and vision selectively where each contributes evidence worth reviewing.

Understand

Keep document structure in view

Use native and visual intake paths to retain page context, layout, tables, figures, forms, handwriting, and relationships—not an undifferentiated text stream. That matters for line-item invoices, Word tables, and business slide decks.

Route

Apply the right kind of analysis

An agent or your application routes approved capabilities to focused specialists, with classifier-led policies available for the standard workflow—for example, adding table analysis to a confidently table-dominant invoice page.

Review

Retain evidence with the outcome

Structured results, specialist artifacts, configuration releases, and operation state are kept together to support review and reproducibility—useful when a business user needs to validate extracted totals, clauses, or slide relationships.

PDF examples: invoices, reports, and archive scans

Use native PDF evidence first; apply OCR or vision only to the pages that need it.

The native PDF processor inspects each page’s text, coordinates, image/vector objects, and tagged structure. It creates an explainable page plan: a digitally readable page can remain native_pdf; an image-only page tries OCR; a page with usable text plus visual meaning becomes hybrid; and a page that needs visual interpretation follows the vision workflow.

1 · InspectRead native text, coordinates, tagged structure, images, and vector objects before rasterizing.
2 · Route a pageSelect the least-expensive path that preserves the page evidence.
native PDFOCRhybridvision
3 · OCR quality gateDoes the OCR have sufficient readable text, meaningful tokens, confidence, and character quality?
Pass · Canonical OCRKeep the schema-valid OCR content tree and its page image.
Escalate · Vision + correlationRetain OCR as evidence, then analyze the same page image for richer structure.
What “better OCR” means here: BADGERS does not assume vision is always more accurate than OCR. It rejects clearly unusable OCR—such as low-confidence, sparse, or symbol-dominated output—and lets the vision path create a richer, correlated document structure from the same page image. Accepted OCR remains a canonical page spine rather than triggering extra vision work by default.

What changes in the output?

Accepted OCR pageProduces a deliberately narrow, line-level content tree. It is efficient for a readable scanned page, but it does not infer table cells or visual relationships.
Vision-correlated pageCan retain a table’s header, rows, cells, reading order, and contributions from multiple specialists, including a flag for human review.
  • OCR quality checks include readable text, meaningful token count, mean line confidence, and readable-character ratio.
  • For a table-dominant page, the configured policy can add table analysis when classification confidence meets its threshold.
  • Both routes leave an artifact trail; the right choice depends on the page evidence.

Word policy example

Keep the Word document’s native structure—and add visual evidence only when it earns its place.

The DOCX processor reads Word OOXML, builds a canonical content-tree XML page, and creates an adaptive page plan. A simple native page stays native_docx; a page needing text recovery may use textract_ocr; and a page with visual-semantic risk may use hybrid or vision_ai. Native structure remains the base for a hybrid result.

1 · Read OOXMLInspect headings, paragraphs, tables, lists, drawings, and their native relationships.
2 · Build a page planProduce a schema-valid native XML spine and route each page independently.
3 · Selective escalationRender only the individual pages that need OCR or visual interpretation.
4 · Preserve provenanceFor a hybrid page, the native DOCX spine remains structural base while vision adds enrichments.
Why native first matters: a Word document already carries reliable structure that a rendered-image OCR pass can flatten. BADGERS can preserve headings and table cells from OOXML, then focus vision on the pages or regions where a visual fact—such as a diagram, drawing, scan, or ambiguous layout—needs interpretation.

Example: procurement policy

Flattened document text“Approval level Amount VP Finance…” may contain the words, but not the explicit header-to-cell relationships or source block identity.
Native + visual structureRetains a real Table with header and data cells, then attaches a visual relationship or evidence note when an embedded diagram needs it.
  • Text-only multi-column content or alignment uncertainty alone does not automatically require vision.
  • OCR is a first-pass option for selected rendered DOCX pages; low-quality OCR can still escalate to vision.
  • The page plan records the route, reasons, fidelity, validation state, and native output URI.

Email and attachment example

Use an application-owned email adapter, then analyze each supported document with a clear trail back to the case.

Raw email formats are not a named native BADGERS intake type. A mail, case, or CRM application owns message parsing, authorization, and retention. It can extract approved attachments or produce an approved representation of message content, store those documents in its private source prefix, and invoke the appropriate BADGERS product per artifact.

1 · Receive safelyThe owning application reads message metadata and enforces its email security, retention, and authorization controls.
2 · Prepare artifactsIdentify supported attachments or create an approved PDF/image representation of relevant message content.
3 · Submit per artifactStore each approved source privately, then send a Headless request or use Full/Specialists as the experience requires.
4 · Rejoin resultsThe application maps its case/email IDs to the returned operation and private artifact pointers for its users.
Boundary to keep explicit: the email-to-document mapping shown below is application-owned, not a BADGERS API response. BADGERS analyzes the supported artifact and returns its own private results. The application remains responsible for safe mail handling, attachment screening, authorization, and showing the result in context.

Example: supplier onboarding email

Mailbox-only viewLeaves the case owner to open multiple attachments and manually connect an invoice, a signed policy DOCX, and a presentation.
Document-aware workflowCreates one case-to-artifact map and attaches structured, reviewable analysis results to each document without treating raw email as an unbounded model input.
  • Use a caller correlation ID to associate an approved request with the application’s case or email record.
  • The Headless request requires a private S3 document URI, session ID, and instruction.
  • The terminal result is a bounded pointer manifest; detailed artifacts remain private in S3.

Same foundation, different boundaries

Choose only the surrounding experience you need.

All three products share specialist packs, configuration releases, artifact storage, IAM, and model-inference foundations. Their difference is the operating surface around that core.

Complete application

For teams operating the complete BADGERS experience.

Full adds the browser workbench, document testing, report viewing, session memory, progress events, operations tooling, and specialist administration around the agent and specialist foundation. Its AgentCore Runtime is VPC-bound, while the UI is internal by default.

✓ Browser UI and reportsTest documents, review page-level output, inspect retained artifacts, and use the operations console.
✓ Agent and GatewayAgent-led specialist orchestration with native PDF, DOCX, PPTX, and supported-image intake.
✓ Collaboration toolsSession memory, progress events, tracing, and the specialist-creation workflow are included.
Application integration

For teams that supply their own user experience or workflow.

Headless retains authenticated agent orchestration, curated specialist packs, a durable private runner, machine identity, and a minimal operation ledger—without the browser application infrastructure. Its VPC-bound runtime uses private subnets. Its default workflow is PDF/image oriented; native DOCX and PPTX templates are selected explicitly.

✓ Versioned request boundaryAuthenticated badgers-agent-request/v1 requests use a private S3 document URI and an instruction.
✓ Durable result pointersCallers receive operation IDs and private status/result manifests; native artifacts remain private in S3.
— No browser UINo ECS UI service, UI identity, report viewer, session memory, or WebSocket handler registration.
Direct tools

For AWS-native code that invokes analyzers directly.

Specialists is the smallest product boundary: selected specialist Lambda packs plus their shared configuration and artifact foundations, called directly through AWS IAM.

✓ Composable packsStart with Document Essentials, add Tables and Forms, or explicitly select additional specialists.
✓ Direct invocationYour application invokes deployed Lambda functions through IAM and consumes the retained result artifacts.
— No orchestration layerNo agent, Gateway, user identity, UI, session memory, or durable operation ledger.
