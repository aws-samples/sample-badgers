Developer experience

Build document intelligence with a boundary that fits your system.

BADGERS separates the document-analysis foundation from the experience around it. Choose a complete workbench, a durable application integration, or direct AWS-native specialist tools.

Start with an integration choice Full · Headless · Specialists

Every option uses versioned configuration and specialist foundations. The difference is who owns the UI, orchestration, and integration boundary.

Choose your boundary

Start with the experience your software needs to own.

Use the tabs to map your developer goal to a BADGERS product boundary and the primary implementation concern.

You need the product surface

Use Full when people need a complete BADGERS workbench.

Full includes the agent, Gateway, enabled specialists, browser UI, reports, session memory, progress events, operations tooling, and specialist authoring. Its AgentCore Runtime is VPC-bound; the optional UI is internal by default. Extend it when your team wants to operate and review BADGERS directly rather than recreate those surfaces elsewhere.

OwnProduct configuration, identity/roles, document experience, and any UI extensions.
ReceiveUI upload/testing, page-level reports, observability, and administration surfaces.
Best next questionWhich people need to test, review, observe, or manage document analysis?
You own the user experience

Use Headless when BADGERS becomes a capability inside your application.

Headless exposes an authenticated, versioned request boundary that accepts a private S3 document URI and instruction. It creates a durable operation and returns private status/result pointers, while BADGERS retains agent-led orchestration and selected specialist packs in a VPC-bound runtime.

OwnYour UI, submission experience, caller credentials, status display, and business workflow.
ReceiveDurable operation IDs, deterministic workflow plans, and private artifact pointers.
Best next questionHow will the application authorize callers and associate an operation with its business record?
You own the orchestration

Use Specialists when your AWS-native code needs focused document tools.

Specialists deploys selected Lambda packs and shared foundations without an agent, Gateway, UI, user identity, or durable operation ledger. Your application invokes a chosen analyzer directly with AWS IAM and owns orchestration around it.

OwnSequencing, retries, user/API boundary, authorization, status, and exception handling.
ReceiveSelected Lambda specialists, versioned configuration, and retained artifacts.

Request and result shape

Headless trades an inline blob for a durable, private operation trail.

A versioned Headless request carries a private document location, session, and instruction. The terminal result contains bounded metadata and private artifact pointers; detailed artifacts stay in the output store.

Why this is developer-friendly

The integration boundary avoids caller-supplied infrastructure references and keeps detailed output out of a broad synchronous response.

  • Request an approved workflow by capability, not Lambda ARN.
  • Store the returned operation ID with your own business record.
  • Retrieve only the declared private result artifacts through the product’s authorized path.

Developer guardrails

Build and deploy only after the product boundary is clear. Keep source documents and detailed artifacts private, do not put credentials or private S3 locations into public documentation, and use the repository’s deployment workflow for infrastructure changes.

  • Use an approved immutable source release; configuration releases pin prompts, schemas, manifests, and routing as one content-addressed deployment artifact.
  • For Headless, use the documented OAuth-protected request path and private tenant source prefix; do not distribute internal Gateway credentials as a generic tool integration.
  • Agent products place the runtime in private VPC subnets with a dedicated security group. Keep the optional Full UI internal unless an explicit public-access requirement is approved.
  • For direct specialists, grant only the intended AWS principals permission to invoke the selected Lambda functions.
  • Validate changes locally with focused tests and profile-aware CDK synthesis before seeking deployment approval.

Considerations for moving into production

BADGERS provides a starting architecture and implementation guidance; it is not a production certification. Follow your organization’s security, privacy, compliance, availability, incident-response, and change-management practices for the workload you are approving.

  • Release ownership: select an approved immutable source release, pin the configuration release, define approvers, and rehearse rollback.
  • Data and access: decide classification, tenant boundaries, retention, residency, audit needs, authorization, and which callers may reach each product boundary.
  • AI behavior: document intended use, untrusted-content and prompt-injection handling, evaluation against representative documents, confidence thresholds, and human-review/failure paths. Research and red-team material may need a deliberately scoped operating environment.
  • Operations: establish SLOs, alert routing, on-call ownership, incident runbooks, quota and capacity review, cost controls, and recovery objectives. The observability plan is a starting point, not a replacement for those decisions.
  • Change assurance: validate the selected profile and integrations in the target account, including regional policy, service quotas, dependencies, and required approvals.

These are ideas to frame an accountable production decision, not a universal checklist or a commitment that a given deployment meets your organization’s requirements.
